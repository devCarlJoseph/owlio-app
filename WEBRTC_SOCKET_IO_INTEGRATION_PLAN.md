# WebRTC + Socket.IO Meeting Integration Plan

## Purpose and status

This document describes meeting integration considerations. Its Socket.IO signaling proposal is not the current implementation or an approved backend contract.

Current frontend state:

- `src/pages/dashboard/classroom/meeting-room.tsx` connects to the existing meeting API and LiveKit client for room media and connected-participant presence. `src/services/api/meeting.service.ts` calls the existing create, join, and end operations.
- The frontend also uses LiveKit reliable data packets for ephemeral in-room chat and hand-raise state. These interactions are not persisted and do not represent official classroom communication or attendance.
- This repository contains the frontend contract only; backend authorization, token grants, and LiveKit deployment must be verified with the backend. Data publishing depends on the issued token allowing it.
- `OWLIO_PRODUCT_PLAN.md` lists full video conferencing as outside the MVP. The current implementation exists in source, but its product priority and production readiness still require owner/backend confirmation.

## Recommended architecture

Use separate responsibilities:

1. **Owlio API** authenticates the user, checks classroom/session membership and permissions, creates or finds the meeting, issues a short-lived meeting credential, and returns ICE configuration.
2. **Socket.IO signaling service** authenticates that credential and relays room presence and WebRTC negotiation messages. It does not carry audio/video.
3. **WebRTC media path** carries audio/video directly between peers for a very small call, or through an SFU for group classes.
4. **STUN** helps peers discover a reachable network address. It does not relay media and will not solve every NAT/firewall case.
5. **TURN** relays media when direct ICE connectivity fails. Plan TURN for a dependable release; use short-lived credentials generated by a trusted backend.

For anything beyond small 1:1 experiments, choose an SFU architecture before implementing group rooms. A full mesh creates a peer connection and upload for every other participant, which scales poorly. Evaluate an SFU such as LiveKit, mediasoup, or Janus against product, hosting, and operational needs; no provider is selected by this plan.

## Decisions required before production work

- Confirm that video meetings are prioritized despite their current MVP exclusion.
- Confirm classroom/session ownership, membership rules, educator controls, learner access, and any waiting-room/admission behavior.
- Select a signaling deployment and decide whether it belongs in the existing backend or a separate service.
- Choose peer-to-peer limits versus an SFU, expected room sizes, regions, and reliability targets.
- Select STUN/TURN hosting, bandwidth/cost limits, credential lifetime, and retention/logging policy.
- Decide whether meeting chat is ephemeral or persisted, and whether recording, captions, or transcripts are in scope. Do not assume consent or retention requirements.
- Confirm the authenticated identity/role contract with the backend. Frontend route prefixes and onboarding choices are not authorization.

## Proposed join and media lifecycle

1. The user enters a meeting attached to an authorized classroom lesson/session. The browser asks for camera/microphone permission only after an explicit user action.
2. The frontend calls an approved Owlio API operation to join. The backend verifies the authenticated account, membership, meeting state, and room policy.
3. The backend returns a meeting ID, participant ID, short-lived meeting credential, and `iceServers` configuration. Never put long-lived auth tokens in a URL or Socket.IO query string.
4. The client opens a secure Socket.IO connection and requests entry to that meeting. The signaling service independently validates the credential and authorization before adding the socket to a room.
5. The service returns the authorized participant roster and emits presence updates. It must not trust a client-supplied display name, role, or classroom membership.
6. The frontend creates an `RTCPeerConnection` using the returned ICE servers, adds local media tracks, and exchanges SDP offers/answers and trickled ICE candidates over Socket.IO.
7. Remote media arrives through `RTCPeerConnection.ontrack` and is rendered in participant tiles. Mic/camera/presentation state is sent as separate, validated room events.
8. On leave, disconnect, or route teardown, the client stops local tracks, closes peer connections, removes Socket.IO listeners, leaves the room, and the server clears presence. Handle reconnect as a new authorized state transition.

## Provisional signaling event contract

Names and payloads below are examples to review with the backend team. They are not existing Owlio routes or events. Version the contract and validate every payload on the server.

| Direction | Event | Purpose |
|---|---|---|
| Client -> server | `meeting:join` | Request entry using the short-lived meeting credential. |
| Server -> client (ack) | `meeting:joined` | Return the server-authorized participant ID and current roster. |
| Server -> client | `participant:joined` / `participant:left` | Publish room presence changes. |
| Client -> target peer (via server) | `rtc:offer` / `rtc:answer` | Relay SDP negotiation for an authorized peer connection. |
| Client -> target peer (via server) | `rtc:ice-candidate` | Relay one trickled ICE candidate. |
| Client -> server -> room | `participant:state` | Publish allowed state such as muted, camera disabled, or hand raised. |
| Client -> server | `meeting:leave` | Leave explicitly; also clean up on socket disconnect. |
| Server -> client | `meeting:error` | Return a safe, structured error such as denied, full, expired, or unavailable. |

For 1:1 peer negotiation, route SDP/candidate events to the intended participant ID and verify that both participants are still authorized members of the same meeting. For an SFU, the negotiation flow is provider-specific; use the SFU's supported client protocol rather than relaying peer-to-peer SDP between every participant.

Do not send video frames, audio, passwords, raw cookies, or long-lived credentials through signaling events. Avoid logging SDP, ICE candidates, or private chat by default.

## Frontend implementation sequence

### Phase 1: contract and service boundary

- Agree request/response and event schemas with the backend and document room state transitions.
- Add typed meeting API and signaling modules beside `src/services/api/`; keep room UI components focused on display and interactions.
- Add `socket.io-client` only after a backend Socket.IO service and authentication handshake are approved. Keep the Socket.IO server dependency in its backend repository/service.
- Map backend errors to concise states: joining, denied, expired, unavailable, reconnecting, and ended.

### Phase 2: local WebRTC lifecycle

- Extract media/device lifecycle from the page into a hook or service: request devices on user action, retain streams in refs/state, and stop tracks on disable/leave/unmount.
- Construct and close `RTCPeerConnection` instances through a tested lifecycle module. Register and remove handlers for `icecandidate`, `track`, and `connectionstatechange`.
- Render remote streams by server-issued participant ID; keep demo participants visibly demo-only and remove them from production data paths.
- Connect camera/microphone controls to real `MediaStreamTrack.enabled` state. Use `getDisplayMedia` on explicit presentation action and replace/add tracks according to the selected peer/SFU design.
- Keep the current local auto-framing strictly local. Do not upload face-detection results.

### Phase 3: signaling and presence

- Join only after backend authorization; register listeners before negotiation to avoid missing early events.
- Use acknowledgements/timeouts for join and negotiation requests. Make join/leave safe to retry and clean up stale sockets on disconnect.
- Handle candidate arrival before a remote description is set by queueing candidates until `setRemoteDescription` succeeds.
- Add reconnect behavior that revalidates the meeting credential and reconstructs necessary connections; do not assume the old socket or peer connection survived.
- Keep chat independent from media signaling. Persist or broadcast chat only after its authorization, retention, and privacy rules are approved.

### Phase 4: TURN, deployment, and release

- Configure HTTPS/WSS and a strict origin allowlist. Use secure cookies or a short-lived, audience-limited meeting credential for socket authentication.
- Deploy TURN (commonly coturn or a managed service) and issue time-limited credentials from the backend. Never ship static TURN secrets in Vite `VITE_*` variables or the browser bundle.
- Exercise ICE candidates over common network types, including restrictive NATs/firewalls. Confirm TURN relay works; STUN-only success on a local network is not sufficient.
- Load-test representative room sizes, bitrate, reconnect churn, and server bandwidth. Monitor connection state and aggregate failure rates without collecting unnecessary media/private payloads.

## Security, privacy, and accessibility

- Enforce authorization on every API operation and every Socket.IO room join/event. Treat all client fields and UI role switches as untrusted.
- Validate payload size/schema, room membership, target participant, and event rate. Use WSS, CSRF/session protections where applicable, origin checks, and short-lived meeting credentials.
- Do not claim attendance, recording, captions, chat delivery, or a participant's identity unless the backend/service authoritatively reports it.
- Explain camera/microphone/screen permissions before requesting them; provide visible device and connection states, permission-denied recovery, keyboard-operable controls, and reduced-motion-compatible status changes.
- Obtain explicit product/privacy approval before recording, transcription, storage, analytics tied to learners, or retention of chat/meeting metadata.

## Verification checklist

- Authorized member can join; non-member, expired credential, ended room, and unauthorized role are rejected server-side.
- Camera/microphone denied, missing, unplugged, or switched during a call produces a recoverable UI state and releases old tracks.
- Two clients can negotiate and exchange media through direct ICE where possible and TURN relay where required.
- Group topology meets the approved room-size target; an SFU is tested if selected.
- Late ICE candidates, duplicate join/leave, tab close, socket reconnect, network loss, and stale participant cleanup are covered.
- Chat, presence, media state, and leave behavior never imply persistence or delivery beyond the actual backend contract.
- Run focused frontend lint/build, backend tests, signaling integration tests, and browser/device permission checks before release.

## Definition of done

The feature is ready for production only when the backend contract, room authorization, signaling service, media topology, TURN deployment, privacy decisions, reconnection behavior, and end-to-end tests are approved and working. Until then, the meeting room remains a local UI preview and must continue to label mock participants and local-only interactions clearly.
