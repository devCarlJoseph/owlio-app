# Owlio AI Implementation Plan

This document defines the proposed approach for adding role-aware AI assistance to Owlio using local/self-hosted model inference rather than a public hosted AI API.

## Recommendation

Use an open-weight model behind an Owlio-controlled inference service:

- **Development:** Run a local model runtime on the developer’s computer. Ollama is a candidate for a simple local setup.
- **Production:** Run the selected model on Owlio-controlled VPS infrastructure, reachable only by the Owlio backend over a private network.
- **Frontend:** Call an authenticated Owlio API contract. Never call a model provider or an exposed model-runtime port directly from the browser.

Avoid relying on a public “free AI API” for production. Free hosted tiers may have changing limits, availability, terms, and data handling. Model weights may be available without a usage fee, subject to their licenses, but inference still has costs for VPS compute, storage, bandwidth, operations, and monitoring. Benchmark before choosing a production model or purchasing a GPU VPS.

## Confirmed Scope

- Plan for all four workspaces: student, school educator, ESL teacher, and tutor.
- Phase the rollout: educator, ESL, and tutor preparation/drafting first; keep student-facing AI disabled until its own age, safety, source, and privacy decisions are approved.
- Start with English-only generation.
- Send only user-entered task context and settings. Do not include learner names, learner records, private notes, or submissions in prompts.
- When a local model is unavailable, provide a clearly labeled static UI preview. Do not imply the preview was generated by AI.
- VPS budget, hardware, expected concurrency, and response-time targets are undecided and must be benchmarked.
- This repository contains the React frontend and API clients, not the backend implementation. Backend service work and VPS provisioning require the backend/deployment repository and owner.

## Current State

- `src/pages/dashboard/ai-assistant/index.tsx` is a shared informational page; it states AI generation is not connected.
- The role workflow plans describe separate educator, ESL, tutor, and student capabilities. Generated professional content must remain a draft under human review and must not autonomously publish, assign, message learners, grade, or modify official records.
- There is no AI service, model runtime, or AI dependency in the frontend.
- `src/lib/api-mode.ts` currently pauses API integrations globally for UI work. AI enablement must be separate; do not turn on unrelated API integrations just to activate AI.

## Proposed Architecture

```text
Owlio browser UI
    -> authenticated Owlio AI API
        -> private inference runtime
            -> selected open-weight model
```

- The backend authenticates the user, enforces role authorization, validates and limits request fields, calls the private inference runtime, validates the response, and returns a typed draft.
- The exact route and request/response schema must be agreed with the backend owner; this document does not establish an API contract or endpoint.
- Configure the local backend to reach a developer’s local runtime and the production backend to reach the private VPS runtime.
- Keep runtime addresses, model selection, and credentials server-side. Never place secrets or private runtime addresses in `VITE_*` values.
- Bind local inference to localhost. Do not publicly expose an unauthenticated model API. Apply authentication, rate limits, request-size limits, timeouts, and safe error handling at the Owlio API.
- Avoid retaining prompt or response content in logs by default. Establish approved retention and operational monitoring before production.
- Keep model/runtime availability separate from the existing global API integration switch.

## Role Experiences and Phases

### Phase 0: Contract and model evaluation

- Agree on authentication, role authorization, request/response schema, limits, timeouts, error behavior, privacy, logging/retention, and health reporting with the backend owner.
- Create a small English benchmark set for question drafting, assignment instructions, lesson activities, and feedback suggestions.
- Evaluate candidate models and runtimes for output quality, license, response time, context size, memory/VRAM use, and expected concurrency on developer hardware and representative VPS capacity.
- Do not commit to a production model or VPS size until the benchmark results are reviewed.

### Phase 1: Educator, ESL, and tutor preparation

- Replace the shared generic page with role-appropriate experiences while retaining role-prefixed routes.
- **Educator:** Draft questions, answer options, criteria, and assignment instructions. Require educator review/edit/reject before any separate save or publish flow. Confirm an authorized destination class before publishing.
- **ESL teacher:** Draft English-language vocabulary, grammar, conversation, reading, writing, or speaking activities from teacher-entered objectives and levels. Do not infer proficiency or claim standards alignment.
- **Tutor:** Draft tutor-facing session plans, practice activities, or feedback suggestions. Do not present the feature as an autonomous learner-facing tutor or a school-grade tool.
- Make generated output visibly identifiable as a draft and editable. Generation alone must not persist, publish, assign, message learners, set mastery, finalize grades, or change attendance/progress.

### Phase 2: Student study assistant (approval-gated)

- Keep student generation disabled until allowed tasks/subjects, age-appropriate behavior, sources/material access, safety handling, privacy/retention, and consent requirements are approved.
- Build a distinct student experience; do not relabel the educator assistant or expose educator/tutor data and actions.
- If approvals remain open, retain only disabled or explanatory UI.

## Frontend Implementation Areas

- `src/pages/dashboard/ai-assistant/index.tsx`: replace the current explanation-only shared content with role-aware or role-specific route adapters.
- `src/pages/dashboard/<role>/ai-assistant/index.tsx`: add thin role-specific adapters if required by the approved route design; keep student generation disabled until approved.
- `src/components/features/ai-assistant/`: add role-specific forms, schemas, state, draft review/edit controls, and unavailable/retry states.
- `src/services/api/ai-assistant.service.ts` and `src/services/api/api.types.ts`: add the client and types only after backend approval.
- `src/main.tsx` and `src/components/common/dashboard-navigation.ts`: keep role-prefixed routes and navigation synchronized.
- `src/lib/api-mode.ts`: preserve the current global UI-only mode; do not enable unrelated integrations as a side effect of enabling AI.

No backend paths are specified because that source is not in this repository.

## Acceptance Criteria

- Production prompts are processed by an Owlio-controlled self-hosted model, not a public third-party inference API.
- The browser communicates only with the authenticated, role-authorized Owlio API. Model credentials and private runtime addresses are never bundled into frontend code.
- Initial prompts use only approved user-entered task context/settings; they exclude learner identifiers, records, private notes, and submissions.
- Educator, ESL, and tutor outputs are clearly labeled editable drafts and cannot autonomously publish, assign, contact learners, grade, set mastery, or change official records.
- Student AI remains disabled until its separate product/safety/privacy gate is approved.
- If local inference is unavailable, the UI shows a clear unavailable state or explicitly labeled static preview, not fake AI output.
- Model and VPS selection follows English-task quality, license, hardware, latency, and concurrency evaluation.
- AI activation does not turn on unrelated APIs or remove existing role-prefixed navigation.

## Verification

- **Frontend tests:** Prompt validation, role-specific UI, disabled/unavailable states, draft editing/rejection, and no false-success behavior.
- **Frontend checks:** `npm.cmd run lint`, `npm.cmd run build`, and `npm.cmd test`.
- **Local integration:** Verify prompts pass through the Owlio API and never directly from browser to model runtime. Test with the runtime stopped.
- **Backend tests:** Authorization, schema validation, request limits, timeouts, malformed model output, and provider-unavailable behavior (in the backend repository).
- **VPS readiness:** Benchmark response time and concurrent requests, verify resource usage and private network exposure, and test restart/rollback.
- **Product review:** Confirm draft/human-review boundaries and role isolation; do not enable student generation before approval.

## Risks and Dependencies

- “Free” weights do not mean a free production service. CPU-only inference may be slow; GPU VPS capacity can increase cost.
- Model licenses and task quality must be checked before adoption.
- Exposing a model server without authentication can expose it to abuse; keep it private behind the Owlio API.
- Backend source, API ownership, and contract approval are required before real generation can be wired.
- Student-facing AI has additional safety and privacy decisions and remains gated.
